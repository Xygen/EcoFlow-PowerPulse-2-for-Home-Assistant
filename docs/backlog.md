# PowerPulse 2 project backlog

This is the **single authoritative list** of open work for this repository.
README files describe current scope, protocol documents retain evidence, and
the changelog records delivered changes; they must link here instead of keeping
parallel TODO or roadmap lists.

When an item is completed, remove it from this file, record the delivered change
in `CHANGELOG.md`, and add the supporting evidence to
`protocol_observations.md` and/or `issue_247_wip_report.md`. Every release must
review those two evidence documents; update `data_paths_overview.md` whenever a
path or field mapping changes.

Any upstream proposal must follow the upstream maintainer's chosen architecture.
This integration's direct C376 MQTT path with bounded PowerOcean HTTP fallback
is project evidence, not a prescription for another repository.

Current implementation baseline: `0.1.1-beta.8`.

| `SAFE-02` | Research paused-state policy | In Solar mode with Continuous charging off, the app reportedly hid the Continuous switch while charging was paused for insufficient solar. ## Telemetry and protocol research

| ID | Priority | Open work | Completion evidence |

| `DATA-02` | Research | Identify the remaining fast-report byte fields `5` and `9`. No-vehicle phase, maximum-current and Solar-minimum-current comparisons left both unchanged while known fields `7`, `4` and `6` changed as expected. Field `5` is an opaque nested block with two four-byte values and two constant `15` varints; field `9` contains only empty/zero nested values. Their function, unit and range remain unresolved, and no further known scalar control is a justified discriminator. Fields `21` (display/LED block) and `31` (Smart settings) are resolved and are not part of this item. See [`docs/protocol_observations.md`](protocol_observations.md). | Compare privacy-safe field structure across a different operating state (connected, charging, paused or completed) or a previously unobserved official-app setting, while recording all mapped values as controls. Only paired evidence may assign a mapping, value range or unit. |
| `DATA-04` | Research | Confirm the unit, scaling and role of `vehicleInfo.currentVehicleComsumption` across additional Smart targets or vehicles. A captured official-app 100 km distance request sent calculated-energy field 3 as `0`; the charger then reported 15000 Wh even though the app's default vehicle was configured for 24 kWh/100 km and the second profile for 20 kWh/100 km. The field was absent from the contemporaneous provider snapshot, so Smart-distance writes must not depend on it. | Controlled 100 km comparisons with each vehicle selected/defaulted establish whether profiles affect a separate backend calculation, when this provider field appears, and what its raw unit means. |
| `DATA-05` | Needs additional operating states | Map additional charger states and `suspend_reason` values. | Captures pair each numeric value with an independently observed app/device state. |
| `DATA-06` | Analysis mostly complete; phase-array evidence validation pending | The Direct heartbeat carries repeated/packed voltage values (field `29`) and current values (field `30`), while the current parser exposes only the maximum of each list. Preserve the existing aggregate entities, but do not create permanent phase-position entities until real `2/33` captures establish snapshot-vs-delta behavior, expected cardinality, stable wire positions, and that voltage/current at the same index represent the same physical position. The parser must also preserve invalid slots so non-finite values cannot shift later positions. See [`docs/phase_measurement_entities_analysis.md`](phase_measurement_entities_analysis.md). | Capture timestamped ordered field `29`/`30` values across unplugged, connected, one-phase, three-phase, load-change and session-boundary states; then implement and test position-stable decoding, anomalous cardinalities, missing/non-finite values, snapshot/freshness semantics, units, default-disabled diagnostics and unchanged existing IDs. Only after voltage/current pairing is confirmed should permanent `phase_1..3` entities be added; `L1/L2/L3` additionally requires physical/electrical reference. |
| `DATA-08` | Research | Investigate the EcoFlow app's historical charging-session report, which attributes delivered energy to PV, grid, and battery. Determine whether the data comes from the already observed `CHARGED_RECORD` family or a separate API/MQTT path, and evaluate a privacy-safe Home Assistant representation without assuming that historical records are live telemetry. | Controlled captures identify the request/response path, session identifier and timestamps, PV/grid/battery fields, units and scaling. Multiple sessions verify that the source contributions reconcile with the reported session energy before any entities, events, or statistics are designed. |
| `DATA-09` | Implemented in `0.1.1-beta.8`; partial live validation | Preserve the original CP307 heartbeat telemetry under consistently named `Wallbox direct` entities and expose the coherent PowerOcean session subset under separate `PowerOcean` entities. Current reporter evidence identifies `241/3` as the PowerPulse 2 (`C376`) accessory-relay path; the equivalent `209/8` form is also decoded. Both require an exact charger-serial match and map only native status, power, session energy and duration; vehicle IDs are discarded and the new path cannot overwrite existing entity unique IDs. The 2026-09-02 charging-session samples confirmed all four PowerOcean entities from this integration, separate source-prefixed unique IDs, and independent in-session progress. A later active-session sample differed by `77 W` (`1285.0 W` Direct versus `1362 W` PowerOcean); the user observed that the PowerOcean value exactly matched the official app display. The sources must therefore remain distinct and must not be presented as interchangeable. | Let this or a later session end and verify a coherent reset for the next session. Then test that the four entities continue to work with the separate EcoFlow integration disabled; confirm the established Direct entity IDs remain unchanged and update independently. |
| `DATA-10` | Research / completeness | Systematically analyse the additional fields carried by the PowerOcean `241/3` and compatible `209/8` wallbox reports: vehicle references and consumption, order/session identifiers and timestamps, operating mode, Plug-and-Play and other settings, grid/phase and OCPP indicators, error/state fields, bitmasks, and currently unknown Protobuf fields. Completeness has priority over avoiding temporary duplicate entities; useful duplicates may be added disabled by default so users can opt in while mappings mature. Privacy-sensitive identifiers must remain excluded or be represented only through a separately approved, privacy-safe design. | Controlled captures across idle, plugged-in, charging, paused and completed sessions establish meaning, units, reset behavior, update cadence and privacy impact for each candidate. Confirmed fields receive source-prefixed entities with appropriate default enablement; unresolved fields remain diagnostics rather than guessed production sensors. |
